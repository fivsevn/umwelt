# 分支维护

[维护总入口](../MAINTENANCE.md) · [验证与发布](deployment.md)

## 日常开发

`main` 保存已经合入的项目内容，也是网页发布来源。开始新工作前更新本地 `main`，从它建立一个用途明确的主题分支；一项工作完成并合入后清理该分支。正在审查的 PR、尚未合入的工作和其他工作区正在使用的分支继续保留。

分支整理只处理 Git 引用，不顺带合入旧实验、重写历史、更新游戏素材或触发发布。文档和目录整理按[整理验证](deployment.md#文档与目录整理验证)确认发布输入保持一致。

## 判断工作是否已合入

先检查工作区状态、所有工作树、本地分支、远程跟踪引用及对应 PR。`git branch --merged main` 可以识别普通合并的祖先关系；它不能完整判断 squash 或 rebase 合并。

遇到 squash 合并，核对 PR 的已合并状态、目标分支、合并时的 head SHA，以及当前分支顶端。当前顶端若比 PR 合并时更新，继续检查新增提交；不能仅凭分支名称、日期或 PR 已合并就删除。没有对应 PR 时，逐项核对提交与实际差异是否已经保存在 `main`。

列表中的 `origin/` 前缀不能代替引用类型判断。用 `git for-each-ref refs/heads refs/remotes` 查看完整名称：`refs/heads/` 是本地分支，`refs/remotes/origin/` 是远程跟踪引用；名字恰好以 `origin/` 开头的本地分支仍属于 `refs/heads/`。同一提交的重复引用不代表多份尚未完成的工作。

## 清理与恢复

清理前在仓库外保存包含全部引用的 Git bundle，核验备份可读，并记录原分支名与提交 SHA。未提交改动、未跟踪文件和忽略的本地原稿另行保存；Git bundle 不包含这些文件。可编辑原稿不能作为缓存批量删除。

先切回干净且与远程一致的 `main`，再逐个删除已经确认完成的本地主题分支。普通合并优先使用 `git branch -d`；squash 合并若需要强制删除，必须先完成上述 PR、提交和备份核对。远程仍有活动 PR 的分支继续保留。

刷新远程引用时可使用 `git fetch --prune origin` 清除服务器上已不存在的远程跟踪引用；这不会删除服务器上的分支。本地分支整理与删除远程分支分开处理，不将批量远程删除纳入日常清理。

本地可以只跟踪 `main`、活动 PR 和仍需核对的历史分支。用 `git config --get-all remote.origin.fetch` 查看当前范围；需要跟踪新远程分支时，先用 `git remote set-branches --add origin <分支名>` 加入，再运行 `git fetch origin`。`git ls-remote --heads origin` 仍可查看服务器上的全部分支。需要恢复全量跟踪时运行 `git remote set-branches origin '*'`，再刷新引用。

完成后检查 `git status`、本地分支及工作树列表，确认没有遗留改动或误占用。需要恢复时，从仓库外备份取回原提交，再按记录的名称重新建立分支。
