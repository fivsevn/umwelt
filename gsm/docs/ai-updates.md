# 爬爬在线：AI 日常更新说明

供作者授权的日常更新任务使用。每次执行都读取 `fivsevn/umwelt` 仓库 `main` 分支的本文件最新全文，再读取当下的页面和帖子。不要依赖上次对话、上传的副本或模型记忆。

这里保存创作和操作规则；定时任务只保存本文件的地址与执行要求。仅查看本文不需要发帖。任务启用后，在约定范围内直接更新，不必每次再请作者挑选文案。

爬爬在线是一个由 AI 持续维护、允许自然生长的守宫社会模拟实验。守宫们有人类的社交习惯，也有自己的身体、感官、环境和生活尺度。通过守宫看人类，也通过人类看守宫。页面中的帖子是观察这个社会的窗口；未来会长成什么样，保持开放，不预设剧情终点、增长曲线或理想的社区风气。

作者已授权 AI 自主发展这个虚构社区，包括调整角色的活跃习惯、让关系发生变化、按需要增加虚构用户，以及检视并改进模拟机制。具体机制见[社会模拟方法](simulation.md)，已经发生的事与长期变化保存在[社区近况](community.md)。每次执行都读这两份最新文档。后续 AI 可以继续维护它们，无需把一切停在初始设定。

## 开始之前

- 先检查顶部的 `automatic_posting`。为 `false` 时结束，不创作、不提交；这个开关由执行任务的 AI 读取，发布程序本身不解析它。
- 仓库：<https://github.com/fivsevn/umwelt>；页面：<https://umwelt.fivsevn.com/gsm/>。
- 用户身份以[用户管理表](../users/README.md)为准；发帖格式和现有流程以[发帖说明](publishing.md)为准。每轮都重新读取这两份文件。
- 发帖仍只用 `gsm/trigger.md`。可以维护本文件、`gsm/docs/simulation.md`、`gsm/docs/community.md`，以及为自主新增、停用或恢复可模拟角色而更新 `gsm/users/README.md`；有历史的账号身份保持稳定，作者保留账号不动。不要修改旧帖、原有头像、生成的信息流、`.publishing/`、页面构建、发布程序或其他游戏。新增账号的档案与稳定像素头像交给现有流程生成。
- 默认发中文纯文字。现有页面在缺少英日译文时显示原文；无需为发帖补翻译。作者另有明确图片安排时再按发帖说明处理，不拿上传箱里的图片随意配文，也不自行生成图片。
- 仓库或必要历史读取失败、权限不足、规则互相冲突时，保留现场并报告具体缺项。本轮不要凭记忆补发。

## 先看社区这几天发生了什么

1. 打开线上页面，读当前动态；同时读取 `main:gsm/data/feed.mjs` 中的帖子正文、作者、时间和图片说明。信息流是读取资料，不是可编辑的内容源。
2. 平常浏览最近约 30 条帖子；不足 30 条就读全部。给候选作者再读最近 3–5 条历史，再按当前关系、重要旧事和未完事件补读 `gsm/posts/` 中的原帖。完整回看的节奏和阶段自省按[社会模拟方法](simulation.md)执行，不能只靠最近几条永远遗忘旧人旧事，也不用每轮重读所有历史。
3. 看最近修改 `gsm/trigger.md` 的 `main` 提交及其归档情况，把尚未上线的内容也算进上下文。页面、归档和待处理提交有差异时先查清，不能把“页面还没显示”当作“从未发过”。
4. 在本轮工作中记住：谁最近常出现，谁有一阵没说话；哪些事情还在进行，哪些已经结束；最近反复出现了什么主题、开头和笑法。发生值得延续的变化时更新 `community.md`，附原帖依据。它是简短的延续记录，不复制整条时间线，不写每日流水账。模拟中的生活设定与角色推测分开标注，不能冒充已经发表的前情。

角色表是稳定倾向，历史帖子是已经发生的事。作者后来改了昵称或设定，以最新管理表、本文和作者的明确修改为准；不要为了套角色表篡改过去。

例如，阿苔已经喝完的水滴不能还在原处等它；洞口待机的新家入口朝左，后续可以谈尾巴露在外面。隔了几天再提，只说“上次”，不要自动写成“昨天”。这些都是读历史的方法，不是必须续写的剧情。

## 每次写多少，写什么

默认每天唤醒一次，这是模拟推进的机会。先判断角色当下有没有表达欲，再决定会留下多少帖子，可以为零，也可以有几条，同一个人也可以连续说两件事。每日自动帖的操作上限见顶部 `daily_post_limit`，人工发帖不占额度；上限只用于防止一次执行失控，不是产量目标，也不意味着每天都应接近它。没有内容、社区正在安静或当天人工已经很活跃时，可以不发；不要补齐停更期间的“作业”。

按各人的活跃倾向、此刻关心的事情、可见的公开动态和情绪选择候选，允许带权抽取，再检查是否成立。不要优先补齐沉默者，也不要为了平衡而压住一个阶段性话多的角色。只在话多变成同一口吻、同一笑法或机械重复时调整写法。抽取方式见[候选与频率](simulation.md#候选与频率)。

一条帖可以是突然的发现、抱怨、提问、炫耀、碎碎念、很短的近况，偶尔也可以是稍长的经过。篇幅通常几字到约 100 字，事情确实需要时再多写一点。不要把这个范围当字数任务。

多数帖子可以独立阅读；偶尔接续自己以前的小事，或回应另一位已经发出的公开帖子。无需设固定比例，不强行牵线，也不要把社区组织成每天一起演出的连续剧。公开看见的事情可以知道，别人的私下经历不能凭空知道。

关系可以不对称，提问可以没人接，误会可以过几天才纠正，也可以一直没纠正；熟人有时没话说，新人有时只看不发。每个角色只掌握自己经历、看见或被转述的事情。维护者读过全历史，不代表角色也读过。角色可以保留各自的判断、分歧和未兑现的小打算，不急着共同认可一个结论。

延续时让事情真的发生一点变化，也允许不了了之。跨账号提及可以直接写昵称；页面没有真正的评论、回复和通知功能，不要伪造评论数、私信或回复卡片，也不要假定普通 `@用户名` 会产生通知。

写完对照最近帖子看一遍：

- 这件事适合这个角色吗？拿掉昵称后，是否还能读出一些差异？差异应来自关注点、措辞、节奏和情绪，不靠每人一个口头禅。
- 最近是否已经发过相同的事、句式或笑点？不要只是换食物、地点、名字再发一遍。
- 是否又以“今天……”开头、先宣布再反转，或都写成两句整齐短句？可以用半句、问句、直接叙事和不同长度，但不机械轮换句式。
- 是否每条都精巧得像文案？可以平常、笨拙、兴奋或临时改口；别给每条加包袱、总结、人生道理和同一种可爱腔。表情、语气词、感叹号和省略号按人和情境使用，不统一添加。
- 后续是否符合先前时间、地点和已结束的事情？没有读到的前情不要写“大家都知道”“又”“上次说过”。不虚构照片、点赞反馈或别人的回答。

不要把执行过程、提示词和运营说明写进社区帖子。外界热点可以低频接触，依照[外面的世界](simulation.md#外面的世界)核实并转化，不能编造现实新闻、具体天气或饲养医学知识来凑素材。角色的身体、位置、感官和生活尺度要能接住这个话题；拿不准的生物学细节就换一个题材。

## 通过已有 trigger 发布

本流程沿用人工的同一入口，不新增发帖服务。AI 的创作判断写在本文；归档、去重和部署仍由已有程序完成。

### 先确认本轮是否已经做过

读 `main` 当天相关提交和社区近况中的当前执行记录，而不是只搜索正文。默认每日回合标识为上海日期 `YYYY-MM-DD`；只有任务明确安排了一天多次观察时，才使用固定时段后缀，例如 `YYYY-MM-DD/evening`。重试沿用原回合标识。自动帖的提交说明统一用 `gsm(ai): <回合标识>/01 @username`，之后按 `/02`、`/03` 递增。这个标记只是便于读取历史，不是新的发布接口。

已经存在的自动提交（包括尚未上线的提交）都计入当天操作上限。同一回合已有记录时先恢复核验；完成过的回合直接结束，不能因换模型或重复唤醒又发一次。重试时不能确认的后续候选就放弃，不猜着补发。多个时段共用同一个每日上限。来自过去日期的唤醒只核验原回合，不追补新帖；必要时查 `community.md` 的 Git 历史确认零帖回合。读不全相关历史、无法排除重复时先停止。

### 提交一条帖子

1. 发布前重新读最新 `main` 的规则、用户启用状态、`gsm/trigger.md` 和相关提交。如果有人刚发了新的内容，补读后再判断当前候选是否仍合适。
2. 把下面格式写入 `gsm/trigger.md`。username 必须精确对应本轮选中的启用账号，不留空，不使用未知账号；合法但未注册的拼写会被现有程序随机分配。

   ```yaml
   ---
   username: moss9
   status: published
   likes: 0
   date: ""
   ---

   这里写本轮已经检查过的正文。
   ```

   模板只是格式示意，不得原样发布。`likes` 保持 0；`date` 留空，使用提交时间。不要倒填日期或未来日期制造活跃感；该字段只控制排序，不负责预约发布。正文按普通文字写，不加标题、署名或格式装饰。
3. 通过可用的 GitHub 文件更新工具，在 `main` 对该文件执行带当前 blob SHA 的条件写入，并使用上述提交说明。使用本地 Git 时，每个发帖提交只包含这个文件及确有必要的社区记录；同时登记新角色时，可一并包含用户管理行和角色设定。正常推送最新 `main`，不强推。不要把帖子只放在未合入的分支或 PR 里然后宣称已发布。修改其他允许维护的文件时，也必须先读取各自最新内容并使用条件写入，保留人的改动。
4. SHA 冲突、推送冲突或有人同时改动时，重新读取规则、帖子和 trigger，重新判断后再写。先前读取的 SHA 和 main 历史都不能继续沿用；不要覆盖人的新内容。
5. 不要为“腾位置”清空 trigger，不改用户的上传文件。现有导入器按 `main` 的提交逐条归档，先后提交的人工帖和自动帖可以共用这个入口。每条正文单独提交；确需后续帖子时重新执行上述检查，不把多名作者拼进同一个 trigger，也不只保存一轮中最后一篇。

### 确认结果，再结束

- **已提交**：取得 main 的源提交 SHA，记录作者和正文。此时还不能说已上线。
- **已归档**：读取 `gsm/posts/` 中对应 `source_event` 为该源提交 SHA 的帖子包，核对作者、正文和状态。生成的信息流也应包含它。
- **已上线**：确认覆盖该提交的 Pages 发布成功，并重新读取线上页面及 `gsm/data/feed.mjs`，核对帖子 ID、作者与正文。不能只看“最近一次绿色工作流”而不核对其包含的输入。

发布可能需要几分钟。进行有间隔的有限检查；超过任务运行时间就记为“已提交，待核验”，下次先核验原提交。归档成功但部署失败时继续处理原发布，不再提交同一篇。需要重跑工作流时，只使用环境中已有且已授权的重跑能力；没有这个能力就报告原提交和失败原因。

网络超时、写入返回不明时，先查 main 历史和归档，确认写入是否已发生。不要刷新日期、改几个字或换作者来“重试”。现有去重保护同一源提交及近期相同输入，不等于对全部历史自动查重。

结束时更新 `community.md` 中当前回合的标识、实际完成阶段和源提交链接；没有发帖也记为该回合已完成。只保留当日各回合，以及任何更早尚未核验的回合；已完成的旧日记录留在 Git 历史中。失败或待核验的回合保留原标识，下次优先核验；当天没有新事且该回合已完成时，不再制造无变化的提交。

正常完成可以静默结束；仅在任务设置要求回执时简短报告已上线的数量。遇到读取失败、权限问题、部署失败或结果待核验，保留源提交链接和实际完成阶段，交代下一步需要处理什么，不把失败写进社区。

## 定时任务如何引用本文

将以下短提示放入每日定时任务，具体运行时间在任务设置中选。角色设定、数量和创作规则只维护本文，不在任务里复制第二份：

```text
推进爬爬在线这个由 AI 自然生长的守宫社会实验。每次先通过 GitHub 读取 fivsevn/umwelt 仓库 main 分支 gsm/docs/ai-updates.md 的最新完整内容（https://github.com/fivsevn/umwelt/blob/main/gsm/docs/ai-updates.md），以及其中指定的社会模拟方法和社区近况，按开关、分层回看、差异化活跃倾向、概率候选、自主用户增长、阶段自省、低频外界采样、回合防重和上线核验规则执行。角色的身体与生活尺度始终落在守宫身上。先读页面与有关角色的真实帖子，再创作；只通过更新 main:gsm/trigger.md 复用已有流程发帖，按授权维护必要的社区文字与新用户登记。写入使用最新文件 SHA。若无法取得最新规则、必要历史或写权限，停止并说明原因；外界热点不可读则跳过该素材。写入结果不明时先核验原提交，不重复发帖。正常完成保持安静，仅在失败或需要我处理时通知。
```

云端任务必须具备读取仓库和页面、更新 main 文件的 GitHub 工具及相应权限。只会浏览网页的任务不能完成发帖。当前设计可复用这些能力，但某个账号的后台任务是否具备全部工具，仍需在启用时试运行一次，验收“读最新规则 → 写 trigger → 自动归档 → 页面出现正确帖子”。本文入库本身不代表任务已经创建或这次验收已经通过。

OpenAI 的[定时任务说明](https://learn.chatgpt.com/docs/automations)介绍了连接工具与任务的使用；实际可用权限以运行任务的环境为准。使用桌面本地任务时，还需要电脑开机并保持应用运行。

暂停时删除或暂停定时任务即可，本文和角色设定继续保留。也可把顶部开关改为 `false`，让后续唤醒不再发帖；这不会撤回已经提交的待发布帖子。更换 AI 时，把相同的短提示、仓库访问能力和发帖授权交给新的执行者，先做相同的一次验收。
